Part 2 — Persistent data and validation (20 points)

The supplied SQLite schema has users, categories, and purchases, with foreign keys enabled. Study it before writing queries. Use parameterized prepared statements with get, all, and run. Never build SQL by concatenating user input.

Complete validatePurchase(body, validCategoryIds). Return {value: {name, quantity, unitPriceCents, categoryId}} when valid, otherwise {error: "useful message"}. Trim names and require 1–100 characters. Quantity must be an integer from 1 to 10,000. unitPriceCents must be an integer from 1 to 100,000,000. categoryId must be an existing integer category ID. Reject Boolean, string, null, missing, NaN, and infinite numeric values. Do not trust values calculated by the browser. Reject an array or non-object request body.

Keep the PA1 UI price in dollars with at most two decimal places. Validate its bounds and cent step before converting to integer cents with Math.round(dollars * 100). Store cents; calculate costCents = quantity × unitPriceCents on the server. Do not accept client-supplied ownerId, costCents, or id as authority. Extra fields may be ignored. Each accepted purchase is separate even when names match.

List purchases using a SQL JOIN that returns the category name, filtered by the logged-in user's ID and ordered by purchase ID ascending. Explain one primary key, two foreign-key relationships, one CHECK constraint, and why relational storage fits these records. Compare with a document-style NoSQL representation in 3–5 sentences.

Grading: validation 8; parameterized SQL, JOIN, and owner-filtered ordering 7; keys, constraints, and SQL/NoSQL explanation 5.

Part 3 — Complete the REST API (20 points)

Method and routeRequired behavior
GET /api/categoriesAuthenticated user receives an array of {id,name} category records.
GET /api/purchasesAuthenticated user receives only their records, each with id, name, quantity, unitPriceCents, categoryId, categoryName, costCents.
POST /api/purchasesValidate and create one purchase for the session user. Return the complete created record.
PUT /api/purchases/:idReplace the four editable fields of an owned purchase after full validation. Return the complete updated record. ID and owner do not change.
DELETE /api/purchases/:idDelete one owned record and return {"ok":true} as JSON. The client must handle the response consistently.

Return 200 for successful reads, updates and deletes; 201 for creation; 400 for malformed JSON, invalid fields, or an invalid positive-integer route ID; 401 when login is required (for mutations, after a valid CSRF check); 404 when the requested purchase does not exist or belongs to another user; and a generic 500 JSON error for unexpected failures. These codes are an API contract, not a memorization exercise. Return errors as {"error":"message"}. For PUT/DELETE, check ownership before modifying. Error cases must not change stored data.

Grading: read and create 8; update and delete 8; consistent errors and no unintended mutation 4.

After login, load categories and purchases. After a successful create, edit, or delete, reload the authoritative purchase list and rebuild history and totals. Totals and count refer only to the current user's purchases. Render names with textContent. Editing loads values into the form; Cancel returns to add mode without a request. Part 5 — Guided authentication and authorization (20 points)

Use the supplied session-cookie helper. Complete these routes with parameterized SQL and Argon2id:

  • POST /api/register: accept email and password. Email is trimmed, lowercase, 3–254 characters and matches a basic non-whitespace user@domain.suffix form. Password is a string of 8–128 characters, without trimming. Store only its Argon2id hash. Duplicate email returns 409; invalid fields return 400. Return 201 with {id,email}, without logging the user in automatically.
  • POST /api/login: verify the stored hash. Invalid credentials return a generic 401. On success, regenerate the session, set userId, explicitly save the session, and then return {id,email}. Never return a hash or password.
  • GET /api/me: return {id,email} for the authenticated user, otherwise 401.
  • POST /api/logout: require authentication, destroy the session and clear the cookie; return {ok:true}.

Use requireAuth on every category and purchase route. Derive ownership from the session, never the request body. The supplied CSRF middleware checks tokens on every mutating API request, including registration, login, and logout. Fetch a token from GET /api/csrf before the first mutation and again after login regenerates the session. In browser requests the Origin must match when present. API clients must keep the session cookie and send the token too.

Keep the provided httpOnly, SameSite=Lax, path, and expiry settings. secure=false is provided only for local HTTP development; HTTPS deployment requires secure cookies. The default MemoryStore is acceptable only for this local exercise. Do not implement JWTs, social login, password reset, real financial transactions, or deployment.

Grading: registration/hash/verification 7; session lifecycle and secrets 5; route/record authorization 6; correct CSRF integration 2.
